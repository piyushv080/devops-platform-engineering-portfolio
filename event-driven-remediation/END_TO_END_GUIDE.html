1. What this project does

This repository demonstrates event-driven operations using Prometheus, Alertmanager, Ansible Rulebook, AWX, Ansible, a disposable Nginx target, and a ServiceNow developer instance. A synthetic page drift triggers an alert. Rulebook starts an AWX job, AWX records the incident, repairs the isolated target, verifies the result independently, and resolves the incident.

Successful end state: target page contains Event-Driven Remediation Service - healthy; AWX run is successful; the linked ServiceNow incident is Resolved and has a resolution note and code.

This is a lab demonstration. Keep credentials out of source control and use only the disposable target for remediation experiments.

Connection directions: Alertmanager → Rulebook uses Compose DNS rulebook:5000. Rulebook → AWX uses the controller URL. AWX → target uses SSH at host.docker.internal:2222. AWX → ServiceNow uses HTTPS and the job credential.

Event sequence

  1. The lab’s drift action replaces the disposable Nginx page with a deliberately noncompliant page.
  2. Blackbox Exporter probes the target URL. Prometheus evaluates probe_success{job="nginx-web-check"} == 0.
  3. After the configured 10-second alert duration, Prometheus sends the firing alert to Alertmanager.
  4. Alertmanager posts to http://rulebook:5000/endpoint. The service name works on the Compose network.
  5. The rulebook accepts the expected alert name, error severity, and allow-listed target, then launches the AWX template.
  6. The playbook validates the event, finds or creates the correlated ServiceNow incident, and writes a detection work note.
  7. Ansible connects to the demo target over SSH, restores the baseline page, and fetches the HTTP page from localhost to verify the marker.
  8. Only after verification passes does the playbook resolve the incident using the instance’s accepted resolution code and a resolution note.

3. Disposable test environment

The Compose file is environment/docker-compose.yml. The event-driven profile includes the services needed for the alert flow. Compose also provides network DNS between containers.

ServicePurposeRelevant access
demo-nginxDisposable Nginx target, SSH server, Ansible userhttp://127.0.0.1:8081, SSH port 2222
blackbox-exporterProbes the demo HTTP page and expected contentCompose network; exporter port 9115
prometheusScrapes the probe and evaluates alert ruleshttp://localhost:9090
alertmanagerDelivers firing alert webhooks to Rulebookhttp://localhost:9093
rulebookRuns Ansible Rulebook and calls AWXInternal endpoint http://rulebook:5000/endpoint

The target is built from nginx:alpine. Its image setup installs OpenSSH and Python, creates the ansible account, unlocks that account for public-key SSH, installs the public key, and allows the lab’s required sudo operations. The private key stays in the local secrets/ folder and is supplied to AWX as a Machine credential.

Network distinction: localhost inside a container means that container. Alertmanager therefore uses Compose DNS rulebook:5000, while the rulebook uses host.docker.internal:8080 to reach AWX on the host. The target inventory also uses host.docker.internal and published SSH port 2222.

4. AWX configuration checklist

AWX runs the automation; the local rulebook submits a launch request to it. Confirm these resources exist and are current:

  1. Project: points to the portfolio Git repository and the branch containing this project. Sync it after code changes.
  2. Inventory: contains the demo target. The host variables need ansible_host: host.docker.internal, ansible_port: 2222, ansible_user: ansible, and ansible_python_interpreter: /usr/bin/python3.
  3. Machine credential: uses the matching private key from secrets/ansible_ed25519 and connects as ansible.
  4. ServiceNow credential: custom credential injects SNOW_INSTANCE_URL, SNOW_USERNAME, and SNOW_PASSWORD into the job environment. The URL is the instance root, for example https://your-instance.service-now.com.
  5. Execution environment: includes Ansible and the required collections/dependencies used by this playbook.
  6. Job template: name must exactly match Incident Remediation - Demo Nginx, organization must be devops-org, and it must use the project, inventory, Machine credential, and ServiceNow credential.
  7. Playbook path: if the AWX project root is the portfolio repository root, use event-driven-remediation/run_event_driven_automation.yml.

Do not create duplicate credentials or reconfigure an already working template. Sync the project after changes, and check the job’s selected project revision when diagnosing a stale run.

5. Credentials and secrets

Expected local files are ignored by Git. Check .gitignore before adding any secret. The rulebook controller token is encrypted with Ansible Vault in secrets/eda-controller.yml; its YAML key is eda_controller_token. The rulebook container also reads its webhook token from the configured secret file.

cd /path/to/your/clone/devops-platform-engineering-portfolio/event-driven-remediation
ansible-vault create secrets/eda-controller.yml

Replace /path/to/your/clone with the directory where you cloned the repository.

Enter YAML content in the editor (substitute your own AWX token; never paste it into this HTML or commit it):

eda_controller_token: "PASTE_YOUR_AWX_TOKEN_IN_THE_VAULT_EDITOR"

The local rulebook launcher reads the encrypted controller token via Vault, prompts for the Vault password as appropriate, then starts the event listener. The Compose rulebook container receives its controller connection settings through environment variables. The ServiceNow password is stored in AWX’s credential record, not in the playbook or this page.

Secret hygiene: a password or token previously pasted into chat, terminal history, a file, or a repository should be rotated. Do not put Basic Auth strings, passwords, tokens, or private-key contents into screenshots or logs.

Expected output: ansible.

6.3 Start the event listener and Alertmanager

For the current Compose-based deployment, run the rulebook in the Compose service. Make sure the AWX controller is reachable at the configured URL and that the controller token is available to the container. If following the repository’s launcher procedure instead, do not start a second listener on the same port.

export EDA_CONTROLLER_TOKEN="$(
  ansible-vault view secrets/eda-controller.yml |
  python -c 'import sys, yaml; print(yaml.safe_load(sys.stdin)["eda_controller_token"])'

export EDA_CONTROLLER_URL=http://host.docker.internal:8080
docker compose -f environment/docker-compose.yml --profile event-driven up -d --build rulebook alertmanager
unset EDA_CONTROLLER_TOKEN EDA_CONTROLLER_URL

Inspect the service state and logs:

docker compose -f environment/docker-compose.yml --profile event-driven ps
docker compose -f environment/docker-compose.yml --profile event-driven logs --since=5m --tail=100 rulebook alertmanager

Open Prometheus at http://localhost:9090/alerts and Alertmanager at http://localhost:9093. An alert should be inactive while the healthy baseline page is served.

7. Test drift and end-to-end remediation

Keep the Compose services running. Run the drift action from the event-driven-remediation directory:

ansible-playbook run_event_driven_automation.yml -e lab_environment_action=drift

This action writes the sample drift page into the disposable target. It does not itself launch the AWX remediation job; Prometheus must detect the failed probe, Alertmanager must deliver the event, and the running Rulebook must launch AWX.

What to watch

  1. Wait longer than the alert’s 10-second hold period.
  2. Prometheus at http://localhost:9090/alerts should show DemoServiceDrift firing with target web_container.
  3. Alertmanager at http://localhost:9093 should show the firing alert.
  4. Watch Rulebook and Alertmanager logs. Rulebook should receive an alert and submit a launch to AWX.
  5. In AWX Jobs, open the newest Incident Remediation - Demo Nginx run. Confirm it has a recent start time and the expected project revision; avoid diagnosing a prior job from the history list.
  6. Follow the job output through incident lookup, detection note, SSH repair, independent HTTP verification, and incident resolution.
  7. Expected outcome is successful job status and a resolved ServiceNow incident with a resolution code and notes.
docker compose -f environment/docker-compose.yml --profile event-driven logs -f rulebook alertmanager

In another terminal, check the restored page after the job completes:

curl -fsS http://127.0.0.1:8081/ | grep -F 'Event-Driven Remediation Service - healthy'

A successful output line containing the marker confirms the page is back to baseline. The playbook’s own verification is also required before it resolves the incident.

Alert timing: the stack scrapes at 5-second intervals, waits 10 seconds for a firing condition, and Alertmanager has a short grouping delay. Allow several scrape cycles for end-to-end delivery.

9. ServiceNow incident lifecycle

The integration uses the Table API and correlates incidents to the alert key (for this run, DemoServiceDrift:web_container). The automation first looks for an active correlated incident, reuses it when found, or creates one if not. It writes a detection work note before modifying the target.

After Nginx has been repaired, the playbook independently fetches the page and asserts that the approved healthy marker is present. Only then does it update the incident to Resolved, supply the instance’s accepted resolution code, and add resolution notes. The successful final record showed Solution provided.

Evidence from the completed run

  • Incident lookup succeeded after transient retries; the job reused INC0010004.
  • The detection work note succeeded after transient retry.
  • SSH connected to web_container; baseline page changed and verification passed.
  • Incident resolution succeeded and the AWX job completed with no failed or unreachable hosts.

ServiceNow errors encountered and what they meant

  • HTTP 401 / “Required to provide Auth information”: credentials missing or not sent; use the credential username/password and Basic Auth only in a secure test.
  • HTTP 500 HTML from snow_adc: transient instance edge/API failure. In this project safe requests retry; configuration uses use_proxy: false so requests do not take an unintended proxy path. Recheck the exact same read request in PowerShell before changing AWX credentials.
  • HTTP 403 with “Resolution code” mandatory: resolution requires a valid resolution choice. This developer instance accepted the display value Solution Provided; the final successful update included that value and resolution notes.
  • HTTP 500 on a journal write: the work-note endpoint may fail transiently even when a separate request works. The automation retries. Check the incident activity history before rerunning because a timed-out journal update may have committed and can create duplicate notes.
  • HTTP 403 reading sys_choice: the API user may not be allowed to read choice metadata. Use the instance UI’s Resolution Information choices or the exact choice already validated in the successful run.
The user account shown in the instance had active itil and sn_incident_write roles. The root cause of the earlier failures was not simply “ITIL missing”: we observed transient ADC 500s and a mandatory resolution-code data policy. The final run confirmed the configured path works.

10. Troubleshooting fixes from this build

SymptomWhat fixed or diagnoses it
cd <path-to-repo> fails or Compose file not foundChange into your actual clone’s devops-platform-engineering-portfolio/event-driven-remediation directory. Run Compose with -f environment/docker-compose.yml from that directory.
SSH says Permission denied (publickey)Check that AWX uses the matching private key and username ansible. The target image had a locked user; its Dockerfile was corrected to unlock it, then rebuilt and recreated. Verify fingerprint matches and run the direct SSH check above.
SSH says remote host identification changedWhen the disposable target is rebuilt, its host key changes. Remove only that lab host/port entry, then reconnect: ssh-keygen -f ~/.ssh/known_hosts -R '[127.0.0.1]:2222'. Do this only for the expected rebuilt lab.
Docker pull fails through a broken credential helperThe Docker Desktop daemon was available, but the WSL client credential helper failed. An empty temporary Docker config successfully pulled the public image: mkdir -p /tmp/docker-anonymous; write {"auths":{}} to its config and run the pull with DOCKER_CONFIG=/tmp/docker-anonymous. This workaround does not replace normal private registry credentials.
Rulebook/Alertmanager cannot reach each otherKeep both on the same Compose network and use http://rulebook:5000/endpoint for Alertmanager’s webhook. Do not use a host-local address from one container to reach another.
Port 5000 is already in useA second locally launched Rulebook listener may be running. Use one deployment mode at a time; the final documented flow runs the rulebook in Compose. Check logs/state before starting another listener.
Container config/mount appears stale after changesRecreate the affected service after changing the Compose config or image: docker compose -f environment/docker-compose.yml --profile event-driven up -d --build --force-recreate rulebook alertmanager.
AWX job is old or uses unexpected codeInspect the newest job ID, start time, selected project revision, project sync, and template. Do not infer current behavior from an older failed run.
ServiceNow lookup or note sometimes returns 500Correlate with the HTTP response body and transaction ID if returned, rerun a safe GET in PowerShell, then inspect the newest AWX run. The completed run passed with retry handling; do not paste credentials or retry a write blindly.
AWX task output hides error due to no_logInspect the sanitized task failure emitted by the playbook or test the matching operation with PowerShell while keeping the password private. The playbook suppresses secrets in output intentionally.

11. Stop and cleanup

Use the project’s stop action to bring down the lab services:

ansible-playbook run_event_driven_automation.yml -e lab_environment_action=stop

Or inspect the Compose profile before manually stopping it:

docker compose -f environment/docker-compose.yml --profile event-driven down

This is a disposable lab. Do not remove volumes or images unless you intend to reset local container state. The ServiceNow incident remains in the developer instance for audit/demo purposes.
